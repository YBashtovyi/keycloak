# Підключення теми КУБ: інструкція для DevOps

Для нового сервера `auth2.kub.army` на dev EKS почніть із
[RUNBOOK-DEV.md](RUNBOOK-DEV.md): контейнер Keycloak 23.0.7, PostgreSQL,
секрети, TLS/DNS, перший realm, перевірка та відновлення.

## Що розгортаємо

| Параметр | Значення |
|---|---|
| Назва теми в Keycloak | `kub` |
| Тип | `login` |
| Версія пакета | `1.0.0` |
| Перевірений сервер | стандартний Keycloak `23.0.7` |
| Батьківська тема | вбудована `keycloak` |
| Мова | українська, включно з резервним словником `en` |
| Залежність від форка | немає |

JAR і ZIP — два способи встановлення **однієї теми**. Пакет містить шаблони,
стилі, логотип, фавікон, шрифти та переклади. Він оформлює вхід, повідомлення
про помилки та пов’язані форми; не змінює внутрішні екрани адмінки, Account
Console, листи, ролі чи налаштування автентифікації.

Для іншої версії Keycloak спочатку перевірте сумісність на staging.
Установлення теми не потребує оновлення версії сервера або міграції БД.

## Які файли передати

Результат збірки знаходиться в `custom-themes/dist/`:

| Файл | Призначення |
|---|---|
| `kub-theme-1.0.0.jar` | Установлення в `providers/`; зручно для образу контейнера |
| `kub-theme-1.0.0.zip` | Папка `kub` для `themes/`, інсталятор і документація |
| `SHA256SUMS` | Контрольні суми обох архівів |
| `DEVOPS.md` | Ця інструкція |
| `INSTALL.md` | Коротка інструкція, включно з Windows |
| `RUNBOOK-DEV.md` | Розгортання нового dev-середовища `auth2.kub.army` |

Якщо обидва архіви лежать поруч із `SHA256SUMS`, перевірте:

```bash
sha256sum -c SHA256SUMS
# На macOS: shasum -a 256 -c SHA256SUMS
```

Достатньо розгорнути один формат. Не залишайте одночасно `themes/kub`
і JAR, який реєструє `kub`, або кілька версій JAR цієї теми.
Попередній артефакт та його контрольну суму збережіть поза каталогом сервера
для можливості відкату.

## Варіант A: сервер Linux, JAR

Приклад нижче припускає `/opt/keycloak` і сервісного користувача `keycloak`.
Замініть їх на фактичні значення вашого середовища.

1. Зупиніть службу Keycloak штатним способом вашого розгортання.
2. Якщо тема вже встановлена, перемістіть попередній JAR у каталог резервних
   артефактів поза `providers/`.
3. Скопіюйте новий JAR із папки релізу:

```bash
install -m 0644 -o keycloak -g keycloak \
  kub-theme-1.0.0.jar /opt/keycloak/providers/kub-theme-1.0.0.jar
```

4. Якщо запуск використовує `--optimized`, від імені користувача сервера
   виконайте `bin/kc.sh build` з тими самими build-time параметрами, які
   використовує ваш сервер. Наприклад, для PostgreSQL:

```bash
cd /opt/keycloak
bin/kc.sh build --db=postgres
```

Збережіть інші наявні параметри збірки: features, health, metrics тощо.
`kc.sh build` готує дистрибутив до запуску; Maven та вихідний код Keycloak
для цього не потрібні.

5. Запустіть наявну службу з її звичними параметрами БД, hostname і TLS.
6. Активуйте тему в потрібному realm за розділом нижче.

## Варіант B: каталог із ZIP

Розпакуйте архів у робочу папку поза каталогом сервера:

```bash
unzip kub-theme-1.0.0.zip
cd kub-theme-1.0.0
bash install.sh /opt/keycloak
```

Інсталятор копіює ресурси до `/opt/keycloak/themes/kub` і не змінює
конфігурацію realm. Правильний кінцевий шлях:

```text
/opt/keycloak/themes/kub/login/theme.properties
```

Користувач сервера повинен мати доступ до читання файлів і проходу каталогів.
Для цього способу зміни ресурсів теми не потребують `kc.sh build`;
після копіювання перезапустіть службу для перечитування кешованих шаблонів
і словників. При переході з JAR спочатку приберіть попередній JAR та
повторіть збірку, якщо сервер працює з `--optimized`.

## Варіант C: Docker та Kubernetes

Для контейнерного розгортання включіть тему до образу. Приклад для
Keycloak 23.0.7 і PostgreSQL; JAR має лежати поруч із Dockerfile:

```dockerfile
FROM quay.io/keycloak/keycloak:23.0.7
COPY --chown=keycloak:keycloak kub-theme-1.0.0.jar /opt/keycloak/providers/
RUN /opt/keycloak/bin/kc.sh build --db=postgres
CMD ["start", "--optimized"]
```

Якщо у вас уже є власний образ Keycloak, додайте `COPY` перед наявним
кроком `kc.sh build`, зберігши його параметри й решту провайдерів.
Образ не повинен містити паролі або параметри підключення до робочої БД.
Передавайте їх існуючим способом розгортання.

Приклад збірки; адресу registry та тег замініть на свої:

```bash
docker build -t registry.example.com/platform/keycloak:23.0.7-kub-1.0.0 .
docker push registry.example.com/platform/keycloak:23.0.7-kub-1.0.0
```

Використовуйте окремий тег або digest для кожного релізу. Не додавайте тему
лише через `kubectl cp` в один запущений pod: після його заміни файли зникнуть.

У Kubernetes оновіть образ через наявний Helm/GitOps-процес. Якщо ресурс
керується без Helm/GitOps, приклад для Deployment `keycloak`, контейнера
`keycloak` і namespace `authentication`:

```bash
kubectl -n authentication set image deployment/keycloak \
  keycloak=registry.example.com/platform/keycloak:23.0.7-kub-1.0.0
kubectl -n authentication rollout status deployment/keycloak --timeout=5m
```

Для StatefulSet використовуйте `statefulset/keycloak` і враховуйте його
налаштовану стратегію оновлення. Збережіть поточні volumes, Secrets,
параметри hostname/proxy/TLS і мережеву конфігурацію.

При першому встановленні активуйте тему **після** доставки образу на всі
репліки. Під час оновлення вже активної теми також завершіть rollout усіх
реплік: за різних версій користувачі можуть бачити різне оформлення.

## Активація в realm

1. Увійдіть до Admin Console та виберіть realm застосунку.
2. Відкрийте **Realm settings → Themes**.
3. У полі **Login theme** виберіть **kub**, натисніть **Save**.
4. За потреби ввімкніть Internationalization у **Localization**, додайте
   `uk` до Supported locales й установіть Default locale: `uk`.
5. Відкрийте нове приватне вікно браузера та перейдіть до входу через застосунок.

Для сторінки входу до адмінки окремо виберіть **Login theme: kub** у realm
`master`. Поле **Admin theme** для цього не використовується.

Вибір теми зберігається в налаштуваннях realm, а не в JAR. Сама доставка
архіву не вмикає тему. Для автоматизації через наявний процес керування realm
відповідне поле — `loginTheme: "kub"`; не імпортуйте цілий realm заради
зміни одного параметра.

Якщо клієнт має власний Login theme override, перевірте і його: він може
перекривати вибір у realm. Realm-перевизначення текстів також мають
пріоритет над словниками пакета.

## Перевірка після розгортання

- У новому сеансі видно заголовок «Вхід до системи», поле «Логін», великий
  логотип із підсвічуванням та українську допомогу. Окремого тексту
  «Тактична система координації та управління боєм БПС» під зображенням немає.
  Напис, що є частиною самого зображення, збережено.
- У Network браузера CSS, WebP і WOFF2 повертають `200`; немає зовнішніх
  запитів до CDN. Ресурси теми мають шлях `/resources/.../login/kub/...`.
- На тестовому обліковому записі перевірено успішний вхід і вихід,
  повідомлення про неправильний пароль та кнопку показу пароля.
- Якщо realm використовує відновлення пароля, реєстрацію, OTP або зовнішній
  IdP, перевірено відповідні кроки; на телефоні немає горизонтального скролу.
- У логах немає помилок завантаження теми або FreeMarker-шаблонів.

Перевірка лише HTTP-доступності сервера не підтверджує, що realm використовує
нову тему; потрібна перевірка самої сторінки входу.

## Оновлення, кеш і відкат

Для наступного релізу збережіть попередній пакет/образ, розгорніть нову
версію обраним способом, перезапустіть усі потрібні інстанси та повторіть
перевірку. Для каталогу спочатку відкладіть стару папку `kub` поза `themes/`
і встановіть нову цілком, щоб не залишати файлів попередньої версії.

Кеш тем у production залишайте ввімкненим. Якщо після заміни ресурсів і
перезапуску видно старий CSS, перевірте кеш браузера та проксі/CDN.
Якщо зберігся файловий кеш Keycloak, під час зупинки відповідного інстансу
можна очистити **лише** `<KEYCLOAK_HOME>/data/tmp/kc-gzip-cache/`.
Каталог `data/` загалом не видаляйте. Перевірте кожну репліку.

Для відкату оформлення поверніть попередній JAR/каталог або попередній
тег/digest образу, повторіть build для optimized JAR-розгортання та
перезапустіть сервери. Назва теми залишається `kub`, тому повторний вибір
у realm не потрібен. У Helm/GitOps виконуйте відкат через той самий процес.

Для повного вимкнення спочатку встановіть штатну Login theme у всіх realm
і клієнтах, де обрано `kub`, а потім приберіть пакет і перезапустіть сервер.

## Типові проблеми

| Симптом | Що перевірити |
|---|---|
| `kub` немає у списку | JAR у `providers/`, restart/build, правильний сервер; у ZIP правильна вкладеність `themes/kub/login` |
| HTML є, але CSS/лого — `404` | Повноту пакета та права; JAR має містити явний запис каталогу `theme/kub/login/resources/` — наш пакувальник його додає |
| Старе оформлення або тексти | Версію на всіх репліках, дубль JAR/каталогу, перезапуск, кеші та client/realm overrides |
| Помилка FreeMarker після оновлення сервера | Сумісність `login.ftl` і `template.ftl` з новою версією; пакет перевірений на 23.0.7 |
| Немає посилання відновлення чи реєстрації | Налаштування realm; тема не вмикає ці можливості |

## Повторна збірка та джерела

З кореня репозиторію, Python 3.9+ без додаткових бібліотек:

```bash
python3 custom-themes/build-package.py
```

Перед публікацією нового релізу змініть `custom-themes/VERSION` і відповідні
версії в документації. `custom-themes/dist/` генерується та ігнорується Git;
передавайте його через сховище артефактів або pipeline.

Перевірено пакування й завантаження JAR на окремому Keycloak 23.0.7 без
папки `themes/kub`, незалежне встановлення ZIP та відтворюваність архівів.
Наведені команди Docker/Kubernetes — приклади для адаптації до середовища,
а не звіт про виконане production-розгортання.

Офіційні довідки: [теми Keycloak](https://www.keycloak.org/ui-customization/themes),
[контейнерні образи](https://www.keycloak.org/server/containers).
